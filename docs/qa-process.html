01 · Processo

Visão Geral do Processo QA

O QA da SolAgora opera em um ciclo contínuo de quatro fases: documentação, automação, execução e reporte. Cada entrega passa obrigatoriamente por todas as fases antes de ser considerada validada.

01 Documentação PO entrega critérios de aceite
02 Revisão QA Checklist de validação doc
03 BDD Escrita dos cenários .feature
04 Automação Implementação steps + POM
05 Execução pytest + Allure evidências
06 Reporte TestPlan + Bug Report
⚡
Regra de ouro: Nenhum cenário é automatizado sem documentação aprovada. Nenhuma execução ocorre sem todos os critérios de aceite cobertos por ao menos um cenário BDD.

Premissas obrigatórias por fase

Fase Responsável Entregável Aprovação de
Documentação Product Owner User Story + Critérios de aceite QA Lead
BDD QA Engineer Feature files revisados PO + Tech Lead
Automação QA Engineer PR com testes passando QA Lead (code review)
Execução QA Engineer / CI Allure Report + evidências Automático (CI gate)
Reporte QA Lead Bug Report + TestPlan atualizado PM + Stakeholder

04 · BDD

Cenários e Steps

Cenários são a unidade central do BDD. Cada cenário deve ser independente, autoexplicativo e cobrindo exatamente um critério de aceite.

Nomenclatura de cenários

TipoPadrão de nomeExemplo
Cenário funcional C<NN> - <Descrição imperativa> C01 - Submeter alteração de e-mail para aprovação
Cenário de gate <N>. <Descrição do fluxo> 1. Realizar login com credenciais válidas
Cenário de bug BUG-<NN>-<A/B/C> — <Comportamento quebrado> BUG-13-A — Campo CPF aceita caracteres especiais

Uso correto de keywords

@clientes_edicao @fluxo_aprovacao @smoke_test @P1
Cenário: C01 - Submeter alteração exclusiva de e-mail para aprovação
  Quando acesso a opção "Editar" do menu de ações do cliente
  E altero o e-mail para um endereço válido e único
  E submeto o formulário
  Então o sistema exibe confirmação de envio para aprovação
  E o status do cliente passa para "Aguardando aprovação"

Cenário de bug com keyword Mas

@bug @validacao @critico @BUG-13
Cenário: BUG-13-A — Campo CPF não rejeita caracteres especiais
  Quando acesso o formulário de nova simulação
  E preencho o campo CPF com "123.456.789-AB"
  Então o sistema deveria exibir erro de formato inválido
  Mas o campo aceita a entrada sem nenhuma validação
✓
Regra do Mas: a keyword Mas (But) é reservada exclusivamente para documentar comportamento atual quebrado. Indica o gap entre o esperado (na linha Então) e o que realmente acontece (na linha Mas).

Proibições na escrita de steps

Proibido Steps com detalhes de implementação: "clicar no botão com id='btn-save'"
Proibido Steps duplicando contexto: step que já está no Contexto: block
Proibido Mais de uma ação por step: "E preencho o CPF e clico em salvar"
Proibido Steps em inglês num arquivo com # language: pt
05 · BDD

Tags e Marcadores

Tags controlam execução seletiva, priorização e rastreabilidade. Todo cenário deve ter ao mínimo uma tag de módulo e uma tag de prioridade.

CategoriaTags disponíveisUso
Quality Gates @gate01 … @gate09 Identifica a qual gate do pipeline o cenário pertence
Prioridade @P1 @P2 @pr_blocker P1 = blocker de release; P2 = importante não blocker; pr_blocker = bloqueia merge
Execução rápida @smoke @smoke_test Suite mínima de sanidade — deve passar em < 5 min
Módulo funcional @clientes @integradores @auth @portal @fmu Filtragem por área de produto
Subfluxo @clientes_edicao @fluxo_aprovacao @aprovacao_positiva Granularidade dentro do módulo
Bugs @bug @BUG-NN @critico Cenários de regressão para bugs documentados
Tipo de teste @validacao_de_dados @historico @regressao Classificação por objetivo do teste
⚠
Cenários sem tag de prioridade (@P1 ou @P2) não entram na suite de CI. O pipeline rejeita PRs com cenários não tagueados.

Comandos de execução por tag

# Apenas smoke tests
pytest -m smoke --alluredir=./allure-results

# Gate específico
pytest -m gate02 --alluredir=./allure-results

# PR blockers apenas
pytest -m pr_blocker --alluredir=./allure-results

# Módulo + prioridade combinados
pytest -m "clientes and P1" --alluredir=./allure-results
06 · Código

Page Objects — Padrões de Implementação

Page Objects encapsulam 100% da interação com o DOM. Nenhum step definition deve usar localizadores diretamente. Todo comportamento de UI passa pelo POM.

Estrutura obrigatória de uma Page Object

from playwright.sync_api import Page, expect
import allure

class NomeDomainPage:

    def __init__(self, page: Page):
        self.page = page

    @allure.step("Descrição humana da ação executada — {param}")
    def metodo_verbo_substantivo(self, param: str) -> None:
        # lógica de interação com o DOM
        self.page.get_by_role("button", name="Salvar").click()
        self.page.wait_for_load_state("networkidle")
        allure.attach(
            self.page.screenshot(),
            name="Evidencia_Salvar",
            attachment_type=allure.attachment_type.PNG
        )

Hierarquia de localizadores

Use na ordem de preferência. Desça um nível apenas se o anterior for inviável.

NívelEstratégiaExemploQuando usar
1 — Preferido Por role ARIA get_by_role("button", name="Salvar") Sempre que possível — mais resiliente
2 Por label get_by_label("CPF") Campos de formulário com label visível
3 Por texto get_by_text("Editar", exact=True) Links, textos únicos na página
4 Seletor CSS locator(".react-select__control") Componentes PrimeReact sem role acessível
5 Compound locator locator("tr", has_text=cpf) Linhas de tabela identificadas por dado
6 — Último recurso JavaScript eval page.evaluate("() => { ... }") Botões ícone PrimeIcons sem acessibilidade

Estratégias de espera

✅ Preferido
wait_for_load_state("networkidle") após navegação.
expect(locator).to_be_visible(timeout=N) para elementos.
wait_for_function("condition", timeout=N) para estados complexos.
⚠ Aceitável com moderação
wait_for_timeout(N) tolerado até 2000ms para animações UI.
Valores acima de 2000ms exigem comentário justificando o delay.

Nomenclatura de classes e métodos

Classes NomeDomínioContextoPage — ex: CustomersListPage, LoginPage
Métodos públicos verbo_substantivo(param) — ex: preencher_dados_simulacao(cpf)
Métodos privados _verbo_substantivo() — helpers internos com underscore
Arquivos snake_case_page.py em subpasta do módulo

Arquivos de Teste — Padrões

Cada arquivo de teste contém o binding de cenários BDD com as fixtures e decorações Allure. O corpo das funções de teste é sempre pass.

Template de função de teste

@pytest.mark.gate02
@pytest.mark.smoke_test
@pytest.mark.P1
@allure.epic("Portal Integrador — Financiamento")
@allure.feature("Simulação")
@allure.story("Nova Simulação com CPF válido")
@allure.severity(allure.severity_level.CRITICAL)
@scenario('../features/simulacao/gate_02.feature',
          'C01 - Iniciar simulação com CPF aprovado')
def test_c01_iniciar_simulacao_cpf_aprovado():
    pass

Regras de estrutura de arquivos

NívelPadrão de nomeLocal
Gate E2E test_gate_0N_<nome>.py tests/
Subfluxo admin test_<fluxo>.py tests/admin/<módulo>/
Conftest global conftest.py tests/
Conftest módulo conftest.py tests/admin/<módulo>/

Padrão de autenticação por escopo

Gates (E2E completo)
Login executado dentro do _macro_gate01(ctx). Cada teste realiza login completo via UI como parte da cadeia de macros.
Módulos Admin (Customers, etc.)
scope="session" com storage_state() salvo. Login ocorre uma vez por sessão. Todos os testes do módulo herdam a sessão autenticada.
08 · Qualidade de Código

Linting e Verificação Automática

O projeto não possui configuração de linting formal ainda. A adoção das regras abaixo é obrigatória e deve ser implementada via .flake8 + hook de pre-commit.

Configuração recomendada — .flake8

[flake8]
max-line-length = 120
extend-ignore = E203, W503
exclude =
    .venv,
    .git,
    __pycache__,
    allure-results

per-file-ignores =
    # Features e conftest têm linhas mais longas naturalmente
    tests/conftest.py: E501
    utils/hml_client.py: E501

Hook de pre-commit recomendado

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pycqa/flake8
    rev: 7.0.0
    hooks:
      - id: flake8
  - repo: https://github.com/psf/black
    rev: 24.3.0
    hooks:
      - id: black
        args: [--line-length=120]

Regras de revisão manual (code review)

RegraNívelVerificação
Todo método público de POM tem @allure.step() Blocker Code review obrigatório
Sem localizadores CSS genéricos (.p-button, .p-component) Blocker Code review + grep no PR
Credenciais nunca hardcoded — sempre via os.getenv() ou .env Blocker Automated secrets scan
Nenhum time.sleep() maior que 3s sem comentário justificando Alerta Code review
Feature files começam com # language: pt e # Autor: Alerta Verificação CI simples (grep)
Todo cenário tem ao menos uma tag de prioridade (@P1 ou @P2) Alerta Script pytest --collect-only
Funções de teste com corpo pass — sem lógica embutida Aviso Code review

10 · Defeitos

Matriz de Severidade e SLA

A severidade é definida pelo QA Lead na triagem. Impacto no produto e urgência de correção são determinados por esta matriz.

Crítico
Crítico — Sistema inoperante
Funcionalidade core inacessível. Nenhum workaround possível. Bloqueia múltiplos usuários ou o fluxo principal completo.
SLA: Correção em até 4 horas · Hotfix obrigatório
Alto
Alto — Funcionalidade degradada
Funcionalidade importante não funciona corretamente. Workaround parcial existe mas impacta a experiência significativamente.
SLA: Correção em até 24 horas · Sprint atual
Médio
Médio — Comportamento incorreto
Funcionalidade funciona mas com comportamento incorreto ou mensagem errada. Usuário consegue prosseguir mas com atrito.
SLA: Correção em até 72 horas · Próxima sprint
Baixo
Baixo — Cosmético / UX menor
Problema visual, texto errado, alinhamento incorreto. Não afeta o fluxo funcional. Pode ser agendado para backlog.
SLA: Backlog · Priorizado pelo PO

Identificação por nomenclatura

IDs seguem o padrão BUG-G<GATE>-<NN> onde:

  • G<GATE> = gate do pipeline onde o bug ocorre (G1 a G9)
  • NN = número sequencial dentro do gate (01, 02 … 99)
  • Exemplo: BUG-G2-01 = primeiro bug do Gate 02
11 · Documentação

Checklist de Validação de Documentação (PO)

Antes de iniciar qualquer automação, o QA valida a documentação entregue pelo Product Owner. Documentação que não atender a todos os itens obrigatórios é rejeitada e devolvida ao PO para revisão.

Itens obrigatórios — Rejeição se ausente

  • ✕
    Critérios de aceite explícitos
    Cada critério deve ser verificável e binário (passou/falhou). "O sistema deve funcionar bem" não é um critério.
  • ✕
    Fluxo principal (Happy Path) descrito passo a passo
    Sequência de ações do usuário até o resultado esperado. Sem ambiguidade de ordem.
  • ✕
    Pré-condições declaradas
    Estado do sistema antes de o fluxo começar. ex: "Usuário autenticado como Integrador com proposta ativa."
  • ✕
    Resultado esperado definido para cada critério
    O que o sistema deve exibir, retornar ou fazer para que o critério seja considerado satisfeito.
  • ✕
    Regras de negócio referenciadas
    Qualquer validação, fórmula ou restrição de negócio deve ter referência (ex: "CPF válido segundo algoritmo da Receita Federal").
  • ✕
    Massa de dados de teste disponível
    CPFs, CNPJs, e-mails, valores ou arquivos específicos necessários para executar o cenário em HML.

Itens recomendados — Deficiência documentada se ausente

  • ○
    Fluxos alternativos e de erro documentados
    O que acontece quando o usuário insere dados inválidos, quando o sistema está indisponível, quando há timeout.
  • ○
    Limites e valores de fronteira especificados
    Máximo de caracteres, range de valores, formatos aceitos/rejeitados. ex: "Nome aceita 3 a 100 caracteres."
  • ○
    Contratos de API documentados (quando aplicável)
    Endpoints, payloads de request e response esperados para validações que dependem de chamadas de API.
  • ○
    Mockups ou screenshots de referência
    Visualização da tela esperada após a ação. Fundamental para validações de UI que não são puramente funcionais.
  • ○
    Dependências com outros módulos identificadas
    Fluxos que dependem de dados criados em outro módulo ou que impactam outro gate.
  • ○
    Permissões e papéis de usuário especificados
    Quais perfis têm acesso à funcionalidade e quais não têm. Matriz de permissões se relevante.
  • ○
    Comportamento em mobile/responsivo definido
    Se o fluxo deve funcionar em mobile, especificar breakpoints e comportamentos distintos.

Critérios de Rejeição de Documentação

Documentação rejeitada é devolvida ao PO com o motivo específico. O fluxo de automação só inicia após reapresentação e aprovação pelo QA Lead.

🚫
Rejeição automática ocorre quando qualquer item obrigatório do checklist (seção 11) estiver ausente. Não há negociação — a documentação retorna ao PO.

Ciclos de execução e rastreabilidade

🔄 Ciclo de Sprint
Criar um run no TestPlan por sprint. Nomear como Sprint <N> — HML — YYYY-MM-DD. Todos os cenários da sprint devem ter resultado registrado antes do fechamento.
🚀 Ciclo de Release
Smoke + todos os cenários P1 executados. Nenhum bug Crítico ou Alto em aberto. Relatório exportado e aprovado pelo QA Lead antes do deploy em produção.
🔁 Regressão Automática
Cenários marcados com @regressao ou @bug executam no CI a cada PR na branch main. Falha bloqueia o merge automaticamente.
📊 Relatório Allure
Gerado automaticamente pelo CI. URL publicada como artefato do pipeline. Screenshots e logs capturados pelo hook pytest_runtest_makereport.
✓
Critério de done para automação: Um teste é considerado "carregado no TestPlan" quando: (1) o caso existe no TestPlan com título igual ao cenário BDD, (2) o resultado da última execução está atualizado, (3) o relatório Allure está linkado ao caso.
